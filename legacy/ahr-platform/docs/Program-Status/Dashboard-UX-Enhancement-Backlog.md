# AHR Platform — Dashboard UX Enhancement Backlog

**Purpose:** Prioritized list of Dashboard usability improvements, identified 2026-07-21 against the actual current codebase (`apps/web/components/cms/*`, `packages/cms-core/src/*`). Data owner selected these as "want to build" items; none are implemented yet. Order reflects effort vs. value, not commitment to a release.

**Status of each item below:** 🔲 Not started (all items, as of this writing).

## Group 1 — Existing scaffolding, needs wiring only

1. ✅ **Wire up Bulk Actions for real** — DONE (2026-07-21). Added `bulkTransitionEntityStatus` to `packages/content/src/service.ts` (partial-success per-item results, same permission/business-rule path as the single-item `transitionEntityStatus`), a new `POST /api/cms/[entityType]/bulk` Route Handler, and wired real "Publish"/"Archive" bulk actions into `list-client.tsx`. Covered by new tests in `packages/content/tests/service.test.ts` (all 43 tests in the package pass; `apps/web` and `@ahr/content` typecheck clean for the touched files — two pre-existing, unrelated typecheck errors remain in `setting-row.tsx` and `lib/person-photo.ts`, untouched by this change). Closes Decision Log item **A9**.
2. ✅ **Activate column Sort** — DONE (2026-07-21). `packages/cms-core`'s `applyListQuery` already supported `params.sort`; nothing server-side ever read it. Wired the list page (`page.tsx`) and the matching `GET /api/cms/[entityType]` route to read `sort`/`direction` from the URL (validated against an allow-list of the resource's real field names — never an unchecked client string reaching `.order()`), and wired `list-client.tsx`'s `handleSort` to toggle asc/desc and push it into the URL. `admin-table.tsx` now shows a ▲/▼ indicator on the active sort column. No new business logic in `packages/cms-core`/`packages/content`, so no new package tests were needed; all 51 `@ahr/cms-core` tests and all 43 `@ahr/content` tests still pass, and `apps/web` typecheck is clean for every touched file (same two pre-existing, unrelated errors as before remain in `setting-row.tsx`/`lib/person-photo.ts`).
3. ✅ **Visual row indicators** — DONE (2026-07-21). Two parts: (a) status badges are now color-coded per lifecycle status (`admin-table.tsx`'s new `STATUS_COLORS` map) instead of identical gray pills; (b) a real thumbnail column for Person/Work/Project/Event rows, backed by a new batched lookup (`apps/web/lib/entity-thumbnails.ts`) that fetches each visible row's most-recently-uploaded image in a single `.in(...)` query (reusing the "most recent image = current photo" convention already established in `lib/person-photo.ts`, but batched instead of one query per row) and resolves each to a public/signed URL. Other entity types (organizations, awards, categories, etc.) have no media relation at all, so they simply get no thumbnail column — nothing to show there. `npm run lint`/`typecheck` clean for every touched file (same two pre-existing, unrelated errors remain); all `@ahr/content` (43) and `@ahr/media` (39) tests still pass — no new package-level logic was added that needed new tests, since the new code is a thin, display-only Route/page-level helper.

## Group 2 — High value, moderate effort

4. ✅ **Field-based filtering** — DONE (2026-07-21). Every `select`-type field a resource declares (Work's `work_type`, Contribution's `role`, Project's `type`, Category's `domain`, etc. — see `packages/content/src/definitions/*.ts`) now gets its own filter dropdown next to the search box, plus a status dropdown for lifecycle-bearing entities. Filter values live in the URL (`?field_<name>=value`, `?status=value`) so they survive a refresh/bookmark, same as sort. Both `page.tsx` and the dropdown values are allow-listed against the resource's actual declared fields/options — an arbitrary client-supplied field name or value can never reach a raw `.eq()` filter. Also fixed a related bug while touching this: `onSearch`/`onPageChange` used to silently discard the other query params (status, sort, filters) on every search or page change — they now go through the same param-preserving helper as sort. `npm run lint`/`typecheck` clean on every touched file (same two pre-existing, unrelated errors remain); all 43 `@ahr/content` and 51 `@ahr/cms-core` tests still pass (no new package-level logic — the allow-listing lives in `apps/web`, which has no test suite of its own, matching the rest of this app).
5. ✅ **Completeness Dashboard** — DONE (2026-07-21). New page at `/dashboard/completeness`, linked from the sidebar and from a new summary card on Dashboard Home. Entirely entity-agnostic: it derives "incomplete" straight from each entity's own `ResourceDefinition` — any required `bilingual-text` field missing either language, and (for Person/Work/Project/Event, the only types with any media relation at all) zero attached images — with a direct link to each incomplete record's edit screen. No schema change and no new per-entity logic; adding a new entity type or required bilingual field to `packages/content` is automatically picked up. `npm run lint`/`typecheck` clean on every touched file (same two pre-existing, unrelated errors remain); all 43 `@ahr/content`, 51 `@ahr/cms-core`, and 39 `@ahr/media` tests still pass.
6. ✅ **Bulk Media Upload** — DONE (2026-07-21). The upload form's file input now accepts multiple files for one selected owner (`multiple` attribute); each file is uploaded to the existing, unchanged `POST /api/media` endpoint one at a time (sequential by design — this endpoint was never load-tested for concurrent uploads), with a per-file row showing pending/uploading/done/error. One bad file (wrong type, too large, etc.) doesn't lose the rest of the batch — same partial-success principle as bulk CMS actions (#1). A shared caption, if entered, applies to every file in the batch; per-file captions can still be edited individually afterward from the Media Library. No backend change was needed. `npm run lint`/`typecheck` clean (same two pre-existing, unrelated errors remain); all 39 `@ahr/media` tests still pass (this was a client-only change).

## Group 3 — Larger effort

7. ✅ **Quick View / preview panel** — DONE (2026-07-21). Clicking a row now opens a side panel with the record's details (reusing the existing, entity-agnostic `DetailView` — no new read-only layout was built), instead of navigating to a separate page; the "Open →" button still navigates directly to the full edit screen for anyone who wants that. No extra request needed for the panel's data — `genericList` already selects `*`, so every field is already on the row the table has. Closes with the ✕ button, clicking the backdrop, or Escape. `npm run lint`/`typecheck` clean (same two pre-existing, unrelated errors remain); all 43 `@ahr/content` and 51 `@ahr/cms-core` tests still pass (client-only change).
8. ✅ **Inline Edit** — DONE (2026-07-21). Two kinds of fields are now editable directly in the table row, no full edit form needed: (a) any `select`-type field (Work Type, Role, etc.) — becomes a dropdown that calls the existing `PATCH /api/cms/[entityType]/[id]`; (b) status — the status badge becomes a dropdown, but only offering the statuses `status.ts`'s `getAllowedNextStatuses` actually permits from the row's current status (never an arbitrary "jump to any status"), calling the existing `/transition` endpoint so the same contribution-required-before-publish rule still applies. Both use a small per-cell saving/disabled state and a toast on failure. No backend change — both requests reuse endpoints that already existed and were already tested. `npm run lint`/`typecheck` clean (same two pre-existing, unrelated errors remain); all 43 `@ahr/content` and 51 `@ahr/cms-core` tests still pass (client-only change).
9. ✅ **Saved Views** — DONE (2026-07-21). A new "Saved views" bar above each entity list lets the admin name and save the current filter/sort/search combination (the list page's query string) and return to it in one click, or delete a saved view. Stored in `localStorage`, scoped per entity type — deliberately not a new database table/migration, since this is a single-administrator tool with no existing per-user preferences column to attach it to; the real tradeoff (one browser only, not synced across devices) is documented in the component itself. `npm run lint`/`typecheck` clean (same two pre-existing, unrelated errors remain); all 43 `@ahr/content` and 51 `@ahr/cms-core` tests still pass (client-only change, no package-level logic).
10. ✅ **Global Search** — DONE (2026-07-21). A search box in the Dashboard's Top Bar (present on every screen, not just an entity list) submits to a new `/dashboard/search` page, which runs the same `genericList` search every entity list already uses — once per registered entity type in parallel — and shows grouped results with a link straight to each record, plus a "view all N" link into that entity's own filtered list when there are more matches than the preview shows. `npm run lint`/`typecheck` clean.

## Group 4 — Lower priority polish

11. ✅ **Keyboard shortcuts** — DONE (2026-07-21). `n` jumps to "New record", `/` focuses the search box — both on any CMS entity list, both ignored while the admin is already typing in any field (so they never hijack normal text entry, e.g. a title containing the letter "n").

## Additional items surfaced from code inspection (2026-07-21)

12. 🚫 **Activate Revision History — BLOCKED, not implemented.** `packages/cms-core/src/revision.ts`'s own file header states this explicitly: *"The Frozen v1 Database Architecture has no table recording full CONTENT revisions... and this milestone must not add one (Non-Negotiable Rule #4)."* Activating this for real means adding a new database table (a schema/migration decision, not an engineering-effort one) — which the codebase's own documented rule says not to do without that decision being made deliberately. Left as the existing `NoOpRevisionAdapter` (no behavior change). If revision history is genuinely wanted, the next step is deciding to formally revise/lift that rule — not silently working around it here.
13. ✅ **Data export (CSV)** — DONE (2026-07-21), scoped to CSV rather than true `.xlsx`: no xlsx/SheetJS dependency exists in this project today, and CSV opens directly in Excel — a real binary `.xlsx` export is a contained follow-up if specifically needed, not a different design. A new "Export CSV" button (next to "New") on every entity list calls a new `/api/cms/[entityType]/export` route, which honors the exact same status/field-filter/search query params currently applied to the list — "export what I'm looking at," not always-everything.
14. ✅ **Dashboard home stats widgets** — DONE (2026-07-21). A "Content by type" grid on the Dashboard landing page shows a count per entity type, each linking to that entity's list. Reuses `completenessReports` (already fetched for the Completeness card) — zero extra queries added.
15. ✅ **Apply the gold brand theme to the Dashboard — scoped to typography only** — DONE (2026-07-21). `--color-primary` (the gold accent) is a root-level CSS variable already used throughout the Dashboard's existing `bg-primary`/`text-primary` classes — that part was never actually missing. What was missing was the brand fonts (Playfair Display / Readex Pro); a new `.dashboard-theme` class now applies those. The full dark background from `.site-theme` is deliberately **not** applied here — that file's own comment explains why: it "hasn't been audited component-by-component" against the Dashboard's existing light-mode components, and a real dark-mode pass is separate, larger work than a typography change, not something to rush alongside everything else in this batch.
