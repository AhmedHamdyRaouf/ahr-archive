# AHR Platform — Solution Decomposition

## السؤال الذي تجيب عنه هذه الوثيقة
كيف تُقسَّم المعمارية المعتمدة (System Architecture، Service Architecture — Phase 8) إلى وحدات بناء قابلة للتسليم بترتيب منطقي؟

## طبقات البناء بالترتيب

| الطبقة | تعتمد على | لماذا تُبنى أولاً/لاحقًا |
|---|---|---|
| **1. الأساس المركزي** | نظام البيانات المركزي، خدمة الهوية (System/Service Architecture) | كل شيء آخر يعتمد على وجود هوية وبيانات مركزية صالحة |
| **2. خدمات المحتوى الأساسية** | خدمة المحتوى، خدمة الوسائط | تبني على الأساس المركزي، ولا قيمة لأي واجهة عرض بدونها |
| **3. خدمات الحوكمة التشغيلية** | خدمة التحقق، خدمة الإشراف | تعتمد على وجود محتوى فعلي لتُطبَّق عليه |
| **4. طبقة التجربة الأساسية** | نظام التجربة (Sitemap، Navigation — Phase 3/7) | تحتاج محتوى وحوكمة جاهزين لتعرضهما بمعنى |
| **5. خدمات التحسين** | خدمة البحث، خدمة الإشعارات، خدمة التعاون | تُثري التجربة، لا تُعطّل المنصة إن تأخرت |
| **6. طبقة الذكاء الاصطناعي** | خدمة تشغيل الذكاء الاصطناعي | تعتمد على وجود بيانات وحوكمة ناضجة لتُقدِّم توصيات ذات معنى، وليست حرجة لعمل المنصة الأساسي |

## مبدأ الاعتماد لا التزامن

كل طبقة تُبنى بعد نضج الطبقة التي تعتمد عليها، لا بالتوازي الكامل مع الطبقات كافة. هذا لا يعني تسلسلًا زمنيًا صارمًا حرفيًا، بل ترتيب أولوية اعتماد.

## مبدأ الوحدة القابلة للتسليم

كل طبقة أعلاه تُعتبر وحدة تسليم مستقلة قابلة للاختبار والتحقق بمفردها (Testing Architecture)، قبل الانتقال للطبقة التالية.

## ما لا تتضمنه هذه الوثيقة

- لا تحدد ما يدخل ضمن النطاق الأول فعليًا مقابل ما يُؤجَّل (Development Boundaries).
- لا تحدد جدولاً زمنيًا أو تقديرات جهد.
